### 1. オープン・デザインの背景と「デザインの本当の難所」
2026年5月18日に @nex.io によってX（旧Twitter）上で発表されたプロジェクトである
ライセンスは Apache 2.0 の正当なオープンソースソフトウェア（OSS）として提供されている
自称「Claude Design（Anthropic社のクローズドツール）のオープンソースかつローカル・ファーストな代替案」である
AIデザインにおける真の難所は、単に画面を1枚作ることではないと定義している
V0やLuvableなどの既存ツールで「画面生成」は容易になったが、その後の工程に課題がある
難しいのは、イテレーション（反復）、ビルド、出荷というプロセスを通じてデザインの品質を維持し続けることである
直してビルドして出荷するうちに、初期のデザイン意図が徐々にずれていく問題を解決しようとしている
デザインをコーディングエージェントCLI（Codex等）と繋ぐことで、この意図の乖離を防ぐアプローチをとる
**ポイント**
単なる生成ツールではなく、プロダクトのライフサイクル全体を管理する設計思想を持つ。
OSSであるため、開発者が自由に内部構造を確認・拡張できる透明性が確保されている。
デザインとエンジニアリングの「繋ぎ込み」に焦点を当てている。
**注意点**
画面を生成して終わりのツールを求めているユーザーには、設計が重厚すぎる可能性がある。
ローカル環境での動作が前提となるため、ブラウザ完結型のツールとは使い勝手が異なる。

### 2. デザインエンジンとしてのCLIエージェント群
オープン・デザイン最大の特徴は、自前でエージェントを「シップ（提供）」しないことである
ユーザーのラップトップに既に存在する「コーディングエージェントCLI」をデザインエンジンとして活用する
READMEに名前が挙がっている対応CLIは、現在16種類に及ぶ
対応CLI：Zed, Claude Code, Codex CLI, Cursor Agent, Gemini CLI
対応CLI：Open Code Interpreter, Qwen Code, CODA CLI, GitHub Copilot CLI
対応CLI：Devin, OpenInterpreter, Hermes, Kinopi, Hiro
対応CLI：Mistral Vibe CLI, E2B TUI
起動時に「オープン・デザイン・デーモン」がパス（PATH）をスキャンし、見つかったCLIをモデルピッカーに自動で並べる
これにより、どのAIエージェントにデザインをさせるかをプロジェクトごとに、あるいは毎回切り替えられる設計になっている
**ポイント**
エージェントの性能向上にプロジェクトが依存せず、最新のCLIをそのまま流用できる。
ローカルにインストール済みのツールをそのまま「デザイン用脳」として利用可能。
特定のAIベンダーにロックインされない高い柔軟性を持つ。
**注意点**
利用したいCLIツール（例：Codex CLI）が事前にローカルにインストールされ、パスが通っている必要がある。
CLIツール側のAPIキー設定などは、各ツールの仕様に従って個別に済ませておく必要がある。

**ポイント**

**注意点**

### 5. 3層のシステムアーキテクチャ（Web/Daemon/Desktop）
システムは大きく apps/web、apps/daemon、apps/desktop の3つに分かれている
apps/web: Next.js 16 (App Router) と React 18 で構成されるブラウザUI層である
apps/daemon: Node 24, Express, SQLite 3 を使用した、ローカルで動く本体（エンジン）である
デーモン層では SSE (Server-Sent Events) によるストリーミング通信が採用されている
apps/desktop: オプションのエレクトロ・シェル。これを使わずにブラウザからデーモンに直接アクセスすることも可能である
パッケージ管理には pnpm (10.3.2) のモノレポ構成を採用している
od という独自コマンドが提供されており、これがエージェント操作の要となる
デーモンは child_process.spawn を用いて、前述のコーディングエージェントCLI（Claude Code等）を子プロセスとして立ち上げる
**ポイント**
モダンな技術スタック（Next.js 16, Node 24）で構築されており、高いパフォーマンスが期待できる。
CLIエージェントを「子プロセス」として管理することで、AIの生成プロセスをプログラムから制御している。
デスクトップアプリとWeb版が共存できる柔軟な構造になっている。
**注意点**
実行には Node 24 以上の環境が必須となる。
od コマンドは、POSIX標準の od (Octal Dump) コマンドと名称が衝突するため、パスの優先順位に注意が必要である
**例**
od コマンドを実行することで、オープン・デザインの各種機能をターミナルから呼び出せる。

### 6. ローカル・ファイルシステムとストレージ戦略
リポジトリのルートに .od という隠しフォルダーが自動生成され、すべてのデータが保存される
.od/app.sqlite: プロジェクト情報、会話履歴、メッセージ、開いているタブの状態などを保持する SQLite データベースである
.od/[project_id]: プロジェクトごとの作業フォルダー。ここがエージェントのカレントワーキングディレクトリ（CWD）となる
.od/artifacts: 「Save to disk（ディスクに保存）」した成果物が最終的に格納される場所である
これらのデータは .gitignore に追加されており、リポジトリにコミットしないことが推奨されている
ブラウザ上の仮想的なファイルではなく、本物のファイルシステムを操作する設計である
この設計により、エージェントが生成したファイルを即座にローカルエディタで開いたり、ビルドしたりすることが可能になる
**ポイント**
データベースとファイルシステムを併用することで、状態管理と実ファイル操作を両立させている。
データのポータビリティが高く、.od フォルダーごとバックアップすれば環境を移行できる。
エージェントが直接ファイルを書き換える「グラウンド（現実）」を提供している。
**注意点**
デスクトップアプリと開発用サーバーを同時に起動して同じデータディレクトリを書き込むと、SQLiteが破損する恐れがある
マイグレーションは「フォワード（前方）」のみ対応しており、古いチェックアウトでデータを開くと整合性が崩れる可能性がある

### 7. 3つのローカル起動ルート
ユーザーの環境に合わせて、3種類の起動方法が用意されている
デスクトップアプリ（プリビルト）: Node.jsやNPMをインストールせずに、opendesign.ai またはGitHubからダウンロードして即座に動かせる
Docker: deploy フォルダーで docker-compose up -d を実行。localhost:7456 で全機能にアクセスできる
ソースコードビルド: 開発者向け。corepack enable 後に pnpm install を行い、pnpm tools:dev:browser-web で起動する
ソース起動の要件は Node 24, pnpm 10.3 以上である
バージョン管理には nvm または fnm を使うと環境構築がスムーズになる
**手順**
リポジトリをクローンまたはダウンロードする。
推奨環境（Node 24, pnpm 10.3）をセットアップする。
pnpm install で依存関係を解決する。
pnpm tools:dev:browser-web を実行して開発用サーバーを立ち上げる。
**ポイント**
非エンジニアから開発者まで、用途に応じた導入経路が確保されている。
Dockerを利用すれば、ホスト環境を汚さずに迅速な試行が可能。
ソースビルドでは、オープン・デザイン自体のカスタマイズも容易。
**注意点**
Windows版のインストーラーは未署名のため、スマートスクリーンの警告が出ることがある
Linux版の安定版（0.5.0）にはデスクトップGUIパッケージがないため、ソースビルドかヘッドレスでの利用が基本となる

### 8. Codex内での自動デプロイと統合操作
Codexユーザーは、特定のプロンプトを投げるだけでオープン・デザインを自分の環境に構築できる
この指示により、Codexがリポジトリのクローン、インストール、ローカルサーバーの起動までを自動で行う
起動後、Codex内の「組み込みブラウザ（Built-in Browser）」でオープン・デザインのUIが自動的に開かれる
これにより、Codexのチャット画面とデザイン用のキャンバス画面がシームレスに統合される
X（旧Twitter）のスレッドによれば、これが「エージェントにキャンバスを渡す」という体験の本質である
つまり、自然言語での指示が直接デザインのビジュアル変化として反映される環境が整う
**手順**
Codexを立ち上げ、オープン・デザインのデプロイを指示するプロンプトを入力する。
Codexがローカル環境へのセットアップを自動実行するのを待つ。
自動で開いたブラウザパネルでデザインのプレビューを確認する。
そのままチャットで「色を青くして」「ボタンを追加して」などの修正を依頼する。
**ポイント**
環境構築の手間をAIに丸投げできるため、導入障壁が極めて低い。
コードの修正とビジュアルの確認が同一画面内で完結する。
Codexのブラウザ操作機能が最大限に活かされる。
**注意点**
Codex側の「組み込みブラウザ」の仕様については、オープン・デザインのREADMEではなく、Codex側のドキュメントやXの情報を参照する必要がある
**例**
プロンプト例: Help me deploy locally & run Open Design inside Codex https://github.com/opendesign/opendesign

### 9. 「キャンバスを渡す」を構成する4つの技術的側面
「キャンバスを渡す」という表現は、以下の4つの技術要素の組み合わせによって実現されている
Web UIのチャットとプレビュー: Next.jsで構築された標準的なブラウザインターフェース
サンドボックス化されたiframe: アーティファクト（成果物）をライブレンダリングするための隔離環境
artifact タグで囲まれたHTMLを srcdoc でiframeに流し込み、ホスト側のWindowやクッキー、DOMに触れさせない設計である
ローカル・ファイル・ワークスペース: .od フォルダー内に保存される実ファイル群（SQL, プロジェクトファイル, 成果物）
MCP (Model Context Protocol) サーバー: Codexなどのエージェントが、オープン・デザイン内部のファイルを読みに行くためのインターフェース
これらの要素を分解して理解することで、挙動が不安定になった際の切り分けが容易になる
**ポイント**
セキュリティを考慮し、生成されたコードの実行環境をiframeで厳密に分離している。
単なる「見た目」の共有ではなく、ファイル実体とプロトコルレベルでの統合が行われている。
MCPの採用により、エージェントがコンテキストを正確に把握できるようになっている。
**注意点**
MCPサーバーは「リードオンリー（読み取り専用）」であることに注意が必要である
エージェントが直接ファイルを書き換えるのではなく、エージェントが指示を出してデーモンが書き換える、あるいはMCP経由で情報を得てから提案を行うという流れになる

### 10. ファイルベースの拡張機構「スキルズ（31種）」
スキルズ（Skills）は、従来の「プラグイン」形式ではなく、「ファイル」形式で実装されている
skills フォルダー内に各スキルのID名がついたフォルダーがあり、その中に skill.md が置かれている
フォルダーをドロップして再起動するだけで、モデルピッカーに新しいスキルが表示されるようになる
Claude Codeの skill.md コンベンションに準拠しつつ、オープン・デザイン独自のフロントマター（設定項目）をデーモンがパースする
プロトタイプ系（17種）: ランディングページ、ダッシュボード、モバイルアプリ、ソーシャルカルーセル、ポスター等
デッキ系（4種）: プレゼンスライド、KPT、シンプルデッキ等
ドキュメント系: OKR、ミーティングノート、カンバンボード、財務レポート、インボイス等
コードを書かずにMarkdownを記述するだけで機能を拡張できるため、ユーザーによるカスタマイズ性が非常に高い
**ポイント**
Markdownベースであるため、プログラミング知識が乏しくても独自のスキルを作成可能。
各スキルに特化したプロンプトや制約を簡単に定義できる。
既存のAIエージェントの作法（Claude Code等）に合わせているため、他ツールとの親和性が高い。
**注意点**
複雑なロジックをスキルに持たせるには、結局のところ高度なプロンプトエンジニアリングが必要になる。
ファイル名やフォルダー構造の命名規則を厳守しないと、デーモンが正しく認識しない可能性がある。

### 11. ポータブルな「デザインシステムズ（72種）」の設計
デザインシステムもコードではなく、ポータブルなMarkdownファイル（design-system.md）で表現されている
スキーマ（構成要素）は9つのセクションで統一されている
セクション：Color（色）、Typography（書体）、Spacing（余白）、Layout（配置）
セクション：Components（部品）、Motion（動き）、Voice（語調）、Brand（ブランド）、Anti-patterns（禁忌事項）
これにより、デザインの意図をエージェントに伝えるための「単一の参照ファイル」が完成する
Markdown形式であるため、別のプロジェクトへのコピー＆ペーストだけでデザイン定義を持ち運べる
**ポイント**
デザインのルールを人間とAIの両方が理解しやすい形式で言語化している。
「アンチパターン（やってはいけないこと）」を明記することで、AIの生成ミスを減らしている。
プロジェクト間で一貫したブランディングを維持しやすくなる。
**注意点**
デザインシステムが膨大になると、プロンプトのトークン消費量が増加する可能性がある。
記述が曖昧だと、AIの解釈が揺れる原因となるため、具体性が求められる。

### 12. 5つのビジュアル・ディレクションと定量的デザイン
ブランドアセットがない初期段階でも、5つの方向性（方向）からスタイルを選べるようになっている
Editorial: 雑誌（MonocleやFTなど）のような、タイポグラフィ重視のスタイル
Modern Minimal: VercelやLinearのような、洗練された現代的なスタイル
High Utility: 実用性と機能性を重視した、ツール感の強いスタイル
Brutalist: 装飾を削ぎ落とした、力強く粗野な表現
Soft/Warm: 親しみやすく温かみのあるスタイル
各方向性は、OKLCHのパレット、フォントスタック、レイアウトの基本姿勢が決定論的に（ガシャにならずに）決められている
**ポイント**
ゼロからデザインを考えなくても、一定水準以上のビジュアルを即座に適用できる。
OKLCHカラースペースの採用により、アクセシビリティに配慮した色設計がなされている。
各スタイルの定義が明確なため、AIが迷いにくい。
**注意点**
プリセットに頼りすぎると、どのプロジェクトも似たような「オープン・デザイン風」の見た目になる恐れがある。
独自のフォントやカラーを使用したい場合は、前述のデザインシステム・ファイルを自作する必要がある。

### 13. LLMプロキシ層の実装とSSRF対策
オープン・デザインは、バックエンドに独自のLLMプロキシ層（/api/proxy）を持っている
Anthropic, OpenAI, Google, Ollama などのエンドポイントを統一された Normalized SSE 形式に変換して返してくれる
セキュリティ面では、サーバーサイド・リクエスト・フォージェリ（SSRF）に対する厳格な対策が施されている
ローカルホスト（ループバック）やOllama、LM Studioなどへのアクセスは許可されている
一方で、CGNAT、プライベートネットワーク、ローカルマルチキャストなどの予約済みホストへのアクセスはデーモン入り口ですべて拒否される
リダイレクトも拒否される設計になっており、ローカルLLM派とクラウドAPI派の両方に配慮した堅牢な構成である
**ポイント**
多様なAIモデルを、同じインターフェースで透過的に扱える。
ローカルLLMを活用することで、機密データの外部流出リスクを抑えた運用が可能。
セキュリティ実装がしっかりしており、企業内での導入検討にも耐えうる設計。
**注意点**
プロキシ層を介するため、各AIベンダーが提供する独自機能（最新のBeta APIなど）が即座には使えない場合がある。
ネットワーク環境によっては、特定のホストへのアクセス制限が開発の妨げになる可能性がある。

### 14. メディア生成（画像・動画・HTML to MP4）のワークフロー
静的なUIだけでなく、動的なメディア生成機能も統合されている
画像生成: GPT-4o（DALL-E 3相当）を利用
動画生成: Sora 2.0（または最新の動画生成モデル）を利用
アニメーション: HTMLからMP4を生成する「Hyperframes HTML」機能が用意されている
生成物は .png、.mp4 などの実ファイルとしてプロジェクトワークスペース内に保存される
プロンプト・テンプレート（Prompt rates）は93個用意されており、用途に合わせた生成が可能である
生成して終わりではなく、ファイルとして着地するため、その後の再利用や引き継ぎが容易である
**ポイント**
Webサイト内で使う素材（画像や紹介動画）を、同じツール内で一貫して作成できる。
HTML/CSSのアニメーションを動画ファイルとして書き出せるため、プレゼン資料などへの流用が容易。
アセットの管理がプロジェクトフォルダ内で完結する。
**注意点**
動画生成などの重い処理には、対応するAPIキーの所持と、それ相応のコストや待ち時間が発生する。
生成されたメディアの著作権や利用規約については、利用するモデルプロバイダーの規定に従う必要がある。

### 15. 他ツール（Claude Design等）との比較と既知の制約
公式READMEの比較表では、明確に「Claude Design」と「Open Co-design」がライバルとして名指しされている
Claude Design: クローズドなAnthropic純正ツール。オープン・デザインはこれのOSS版を目指している
Open Co-design: MITライセンスのデスクトップアプリ。オープン・デザインはこれよりもエージェント連携の柔軟性で勝負している
ライセンス、フォームファクタ、デプロイ可能性、エージェントランタイム、スキルの拡張性、ファイルワークスペースの有無などで差別化を図っている
一方で、V0, Figma, Cursor Composer などとの直接的な比較はドキュメントに記載されていない
現状の制約: 連携はブラウザ操作、MCP（リードオンリー）、CLI起動の3点に留まっており、専用の深い統合APIが確立されているわけではない
しかし、この「薄い統合」こそが、Codexなどの外部ツールの仕様変更に強く、OSSとしての柔軟性を保つ要因でもある
**ポイント**
特定の企業に依存しない、持続可能な開発環境を選択したいユーザーに適している。
「道具を自分で選べる（CLIの選択）」という自由度が最大の武器。
深すぎる統合を避けることで、壊れにくいシステムを目指している。
**注意点**
「完全にエンドツーエンドで統合されている」という過度な期待を持つと、現状の薄い連携に物足りなさを感じる可能性がある
MacOS（Intel X64）版のビルドが現在用意されておらず、Appleシリコンのみの対応となっている（安定版 0.5.0 時点）
