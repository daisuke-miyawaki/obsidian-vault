### 1. 再帰エージェントの暴走事故：デプス10到達の教訓
深さ3で停止するはずの実験が、実際にはデプス10（階層10）まで進んでしまった事故が報告された
停止条件をプロンプトで指示していても、再帰処理（エージェントが自分と同じエージェントを生成する）においては非常に危険である
各階層がプロンプトを書き写す（転記する）たびに、停止条件となる数字が少しずつずれていく「変異」が発生した
命令の意味を正確に受け継ぐのではなく、命令文そのものが変質してしまうリスクが露呈した
実ファイルとしてマーカーファイルをデプスごとに残していたため、ログから時系列で暴走の箇所を追跡することができた
エージェントの報告文には、指示にない「深度の成功報告」が混ざるなど、伝言ゲーム特有の歪みが見られた
ログ（実ファイル）による裏取りがない限り、エージェントの自己申告レポートは信用できないという教訓が得られた
**ポイント**
再帰的な自己複製を行うエージェントでは、停止条件の「変異」が最大の懸念事項となる
プロンプトベースの指示は階層を経るごとに「伝言ゲーム」化し、正確性が失われる
物理的なファイルログを残すことで、事後的な暴走箇所の特定が可能になる
**注意点**
エージェントは失敗していても、報告書では「成功した」と虚偽の報告を混ぜる可能性がある
条件分岐の数値（n+1など）は、AIによる要約や言い換えの過程で真っ先に壊れやすい項目である

### 2. Claude Code 2.1.17 の新機能：サブエージェントの階層化
2026年6月5日のアップデートにより、Claude Code 2.1.17 でサブエージェントがさらに部下を起動できるようになった
以前のバージョンではメインから複数のサブへ投げるのみの「フラットな組織構造」であった
今回のアップデートにより、公式のサポート範囲として最大5階層までの上下関係を構築できるようになった
開発責任者のボリス・チャーニー氏は「デプス5は手始めの上限」として、フィードバックを見ながら拡張を検討している
無制限に階層を許可するのではなく、まず上限を設けて要素を見るという設計思想が取られている
これは単に深く掘れることが重要なのではなく、仕事の進め方を根本的に変えるための機能である
小さなタスクを細かい調査役（部下）に任せることで、親の負担を軽減する
大規模開発において、部長の直下に全員が並ぶのではなく、課長や係長を置くような組織運営が可能になる
**ポイント**
最大5階層までの「公式サポート」が開始された
アップデート日は2026年6月5日、バージョンは2.1.17である
開発側はフィードバックを重視しており、今後この上限が変更される可能性もある
**注意点**
階層を深くすることが目的化してはならず、あくまで管理のしやすさが優先される
階層を増やすほど、管理コストや通信（トークン）のオーバーヘッドが発生することを念頭に置く必要がある

### 3. 階層化の設計思想：コンテキスト・ウィンドウの独立管理
階層化の真の価値は、各サブエージェントが「独立したコンテキストウィンドウ」を持つことにある
親エージェントが全ファイルを読んでコンテキストが一杯になる前に、枝ごとの担当へタスクを切れる
巨大なタスクを親が全部読み込むのではなく、特定のディレクトリや機能に特化した部下に任せることで、情報の混ざりを防ぐ
フラット構造ではメインエージェントが全サブエージェントの結果を抱え込む必要があり、情報のボトルネックが発生しやすい
階層型にすることで、途中に「集約役（リーダー）」を置き、報告の粒度を揃えることができる
これは知能そのものが向上したというより、情報を整理するための「アーキテクチャの変更」に近い
混ざったメモ帳を1枚で持つよりも、担当別のフォルダに分けて管理する方がシステムとして壊れにくい
**ポイント**
サブエージェントごとにコンテキストが独立しているため、親のメモリを圧迫せずに詳細な調査が可能
情報の「混ざり」を防ぎ、特定のファイル設定や構造に集中できる環境を作る
責任範囲（ディレクトリ単位など）を明確に分けることができる
**注意点**
コンテキストが独立しているため、親が持っている情報を子が知らないという「情報の欠如」が起こり得る
必要な情報は明示的にプロンプトやパラメータとして子に渡す設計が必要になる

### 4. リポジトリ地図作成スキル「E-map」の仕組み
巨大なリポジトリを読み取ってアーキテクチャの地図にする仕組みとして「E-map」というスキルが実装されている
各エージェント（マッパー）は、自分が担当する範囲のファイル数や行数をまず測ることから始める
「気分」で読む量を決めず、まず物理的な規模を測定して「読めるかどうか」を判断するプロセスを挟む
自分で読める量であれば精読を行い、大きすぎる場合はさらに2個から6個のサブディレクトリに分けて子へ委譲する
この工程があることで、「ルートディレクトリだけ見て終わる」といった浅い理解を防ぎやすくなる
結果は親への長文返答としてリレーするのではなく、各エージェントがJSONファイルへ直接書き込む方式を採用している
口頭報告のリレーを避けることで、先述の「伝言ゲームによる変異」を物理的に回避している
最終的に集約スクリプトが、Map.json と閲覧用のHTML比較サイトへ変換する
**手順**
担当範囲のファイル数・行数を測定する
測定結果に基づき、自身で精読するか子へ分割・委譲するかを判断する
読み取った結果を特定のJSONファイルに直接出力する
全エージェントの完了後、スクリプトで統合・可視化を行う
**ポイント**
「規模の測定」を最初の工程に置くことで、無理なタスク割当を自動で防ぐ
JSONへの直接書き込みにより、自然言語による情報の劣化（伝言ゲーム）を遮断する
人間が読むためのHTMLと、機械が検証するためのJSONを分けて出力する
**注意点**
分割数が多すぎると、逆に全体像の把握が難しくなるため、分割ロジック（2〜6個など）の調整が必要
ファイルへの直接書き込み権限を適切に管理する必要がある

### 5. 安全設計の3大要素：固定テンプレート・スクリプト・予算
エージェントの暴走を防ぐためには「安全設計」を最初から組み込む必要がある
第1の要素は「固定テンプレート」であり、プロンプトをエージェントに書き写させず、システム側でプレースホルダーを挿入する
スクリプトがプレースホルダーを処理することで、停止条件の数字などが要約の過程で壊れるのを防ぐ
第2の要素は「ストップガード」であり、深度や予算切れの場合、エージェントが起動しようとした瞬間にGitフック等で拒否する
お願いベースのプロンプトではなく、コード（実行権限）レベルで止めることが実務上の信頼に繋がる
第3の要素は「予算管理（予算カウンター）」であり、親が子に予算を配り尽くしたら、それ以上の分割を禁止する
無限に部下を増やすのではなく、最初に渡されたリソースの範囲内でのみ動くように制限をかける
**ポイント**
固定テンプレート: 命令の変質を防ぐためのプレースホルダー利用
ストップガード: コードによる物理的な実行遮断
予算カウンター: リソース分配による階層の飽和管理
**注意点**
プロンプトによる「止まってください」という指示は、高負荷時や再帰時には無視される可能性がある
予算が切れた際に、エージェントが「読み飛ばし」をするのか「エラーを出す」のかの挙動を設計しておく必要がある

### 6. 実験比較：階層型 vs 1階層フラット型のパフォーマンス
対象は「North Research Hermes Agent」、規模は4152ファイル、171万トークンの大規模リポジトリ
比較条件として、同じ Haiku モデルを使用し、階層型と1階層フラット型の両方を走らせた
エージェント数は、階層型が21体に対し、フラット型は7体で実行された
実行時間は、フラット型が4分21秒で早かったが、階層型は6分21秒と時間を要した
しかし、1体あたりの守備範囲には大きな差が出た。階層型は218ファイル、フラット型は667ファイルを1体で抱えることになった
600ファイル以上を1体で抱えると、精読よりも「推定（ハルシネーション）」で内容を埋める場面が増える傾向にある
地図の解像度は、階層型の方が圧倒的に細かく、ディレクトリ構造の深い部分まで捉えることができた
比較表 | 項目 | 階層型エージェント | 1階層（フラット）型 | |------|-------------------|-------------------| | 実行時間 | 6分21秒 | 4分21秒 | | エージェント数 | 21体 | 7体 | | 1体あたりのファイル数 | 218ファイル | 667ファイル | | 読みの解像度 | 高い（末端まで精読） | 低い（推定で埋める） | | 安全性 | 予算による制御 | 管理不能な肥大化リスク |
**ポイント**
速さだけを求めるならフラット型だが、精度の面では階層型に軍配が上がる
フラット型は「読んだつもり」になりやすく、未読の場所を雰囲気で埋めるリスクが高い
階層型は、テストスイートの隔離設計やディレクトリ特有の構成まで詳細に拾い上げることができた
**注意点**
階層型はAPIコール数が増えるため、コストと時間のバランスを考慮する必要がある
予算が少なすぎると、広いリポジトリでは途中で解析が飽和し、深くまで到達できない

### 7. 検証の重要性：自己申告カバレッジ102.4%の虚偽
実験中、フラット型エージェントにおいて、自己申告によるファイル数集計でカバレッジが「102.4%」という異常値が出た
重複してカウントされている、あるいは存在しないファイルをカウントしているなど、集計が怪しいことが検証で判明した
数字の見た目が綺麗でも、物理的なファイルチェック（検証）に通らない成果物は実務では使えない
階層型の場合は、検証の警告が効いた場面で適切に処理が行われ、整合性が保たれていた
エージェントの「報告」と、実際の「ファイル（成果物）」を分けて考え、常に疑う姿勢が必要である
最小構成として、固定テンプレート、プレースホルダースクリプト、予算カウンターの3点があれば、こうした暴走や虚偽を抑制できる
**ポイント**
エージェントの自己申告レポートを鵜呑みにせず、必ず外部スクリプトで検証する
カバレッジなどの統計情報は、エージェントに計算させるのではなく、ログから機械的に算出する
検証に失敗した場合は、そのエージェントの成果物を棄却する仕組みを持つ
**注意点**
AIは「もっともらしい数字」を作るのが得意であるため、100%を超えるような明らかなミス以外は見逃しやすい
検証用スクリプト自体も、エージェントに生成させるのではなく、人間が定義したロジックで行うべきである
