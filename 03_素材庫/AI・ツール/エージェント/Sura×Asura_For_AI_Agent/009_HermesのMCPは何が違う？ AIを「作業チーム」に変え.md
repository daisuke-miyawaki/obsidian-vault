# HermesのMCPは何が違う？ AIを「作業チーム」に変える入口

テーマ：AIを「作業チーム」に変えるためのMCP（Model Context Protocol）活用とエージェントOS「Hermes」の独自性
結論：Hermesは単なるツール接続に留まらず、接続と運用のレイヤーを統合し、安全なツール制御と他ツールへのサーバー提供を行う「エージェントOS」として機能する
自分への使いどころ：複数エージェントを連携させた開発チームの構築や、Stripe・Slack等の外部APIを安全に（権限を絞って）AIに操作させる基盤として活用する

### 1. MCP（Model Context Protocol）の概要と共通規格化のメリット
MCPは、AIに外部ツール（GitHub、ファイル、DB等）を操作させるための共通規格である
かつてはツールごとに専用の接続プログラム（Slack用、GitHub用など）を個別に書く必要があり、開発コストが高かった
共通規格化されたことで、一つの方式で多様なツールをAIの「手足」として繋げられるようになった
AIは単に「話す相手」から、実際に「動かす・操作する」存在へと変わる
具体的には、GitHubのPR確認、Slackへの返信、データベースからのデータ抽出、ファイルシステムの読み書きなどが可能になる
自前で作成したAPIも、MCPの規格に沿えば即座にAIのツールとして組み込める
現在、多くのツールやサービスが毎週のようにMCP対応のリリースを出している状況にある
**ポイント**
MCPはAIとツールの「繋ぎ込み」を標準化するプロトコル。
特定のサービスに依存せず、共通のインターフェースで拡張可能。
AIが実働を伴う「エージェント」になるための必須技術。
**注意点**
MCP対応ツールを増やすだけでは、複数のAIを扱う際の管理問題は解決しない
単なる「接続」と「運用」は別レイヤーの話として整理する必要がある

### 2. AIエージェント運用の新たな課題：ツール接続後の「誰が何をやるか」
ツールが繋がった後に出てくる悩みは、複数のAIでどう仕事を回すかという運用の問題である
AIに3つも4つも仕事を投げると、「誰が担当しているか」「どこまで進んだか」が不明透明になりやすい
タスクの進捗管理や、次のエージェントへの引き継ぎは、MCPでツールを繋いだだけでは解決しない
現状の多くのMCP対応ツールは、サーバーを追加して便利にする段階で止まっている
Hermesはこの「接続」のレイヤーと「運用」のレイヤーを深く統合している点が他と異なる
個人の作業補助を超えて、チームとしてAIを動かすための土台が求められている
**ポイント**
接続は入り口に過ぎず、その上の「運用レイヤー」が実務の成否を分ける。
複数エージェント環境では、タスクの可視化と担当の明確化が不可欠。
Hermesは接続と運用を「一対の技術」として扱っている
**注意点**
ツールを増やすほど、管理コストが指数関数的に増大するリスクがある。
運用設計がないままMCPを導入すると、作業が破綻しやすい。

### 3. Hermesの最大の特徴：クライアント兼サーバーとしての動作
Hermesは外部MCPツールを使う「クライアント」であると同時に、自身を「MCPサーバー」として公開できる
これにより、他のツール（Claude Code、Cursor、Codex等）からHermesをMCP経由で呼び出すことが可能になる
Hermesが仲介役（ハブ）となり、通信、記憶、作業の基盤を他ツールに提供する構造を持つ
サーバー化することで、TelegramやDiscordのメッセージ履歴や会話コンテキストを外部から扱えるようになる
手元のコーディングツールから、チャットの世界（SNS等の外部通信）へシームレスに手を伸ばせる感覚が得られる
**手順**
ターミナルで hermes mcp serve コマンドを実行する
Hermes自体がMCPサーバーとして立ち上がる
Claude Codeなどの外部ツール側で、このサーバーを設定に追加する
**ポイント**
「使う側」と「使われる側」の両方の機能を備えている。
通信（Discord等）と記憶を統合した「ハブ」として機能。
ツール間の壁を取り払い、既存のコーディングエージェントに新機能を追加できる。

### 4. ツール競合を防ぐ名称管理：プレフィックスとランタイムツールセット
複数のMCPサーバーを繋ぐと、同じ「read」や「search」という名前のツールが衝突する問題が起きる
,
Hermesは読み込んだツール名の頭に mcp_ やサービス名のプレフィックスを自動で付与する
例：mcp_github_create_issue や mcp_filesystem_read_file のように登録される
これにより、Hermes標準ツールと外部MCPツールが名前でぶつかることを防げる
ツールを大量に追加しても、どのツールがどのサーバー由来かを見失わない
サーバーごとに「ランタイムツールセット」としてツールをひとまとめに管理している
接続をどれだけ増やしても管理が破綻しないよう、土台から整理されている
**ポイント**
自動プレフィックス付与により、ツール名の衝突を技術的に回避。
mcp_サービス名_機能名 という規則的な命名によりAIがツールを選びやすくなる。
サーバー単位のまとまり（ツールセット）で扱うため、拡張しても散らからない。

### 5. 実務に必須の安全設計：サーバー単位のツール・フィルタリング
HermesのMCPは、サーバー内で使用できるツールを個別に絞り込む機能を備えている
安全なツールだけを「インクルード（許可）」し、危険なツールを「エクスクルード（除外）」する設定が可能
特定のサーバー丸ごとを無効化することもでき、柔軟な権限管理が行える
MCPツールは「便利なもの」と「危ないもの」が同じパッケージに入っていることが多いため、この制御は実務で極めて重要になる
権限を絞ることで、AIが意図しない破壊的な操作（データの削除、返金処理など）を行うリスクを最小化できる
設計段階から「安全な小出し」ができるよう考慮されているのがHermesの強みである
**ポイント**
Include/Excludeリストによる詳細な権限制御。
サーバー単位でのオン/オフ切り替え。
AIに「見せるツール」を人間が事前に選別できる。
**注意点**
全部のツールを無条件で見せると、AIが気を利かせて誤操作をする恐れがある
権限管理を後付けで実装するのは困難なため、接続時に設定することが推奨される

### 6. セキュリティの具体例：StripeやSlackにおける操作制限
Stripe（決済）の例
,
安全な操作：「顧客を検索する」「請求履歴を見る」などはAIに許可する。
危険な操作：「返金する」「新規課金を作成する」などのお金が動く操作は隠しておく。
Slackの例
許可：「メッセージを投稿する」操作。
制限：「チャンネルを削除する」などの管理操作は隠蔽する。
データベースの例
許可：データの読み取り（SELECT）。
制限：テーブルの削除（DROP）やデータの改ざん。
このように、サービスごとに提供されている機能の中から、AIに任せて良い範囲だけを切り出すことができる
**例**
Stripe MCP連携時の設定例：
include: search_customers, list_invoices
exclude: create_refund, delete_customer

### 7. クラウドMCP対応：STDIOからHTTP/OAuth 2.0への拡張
当初のMCPはローカルPCで動かす STDIO 方式が中心だったが、現在はクラウド連携への対応が進んでいる
Hermesはネットワーク（HTTP/HTTPS）で繋ぐタイプのMCPサーバーに対応している
さらに、OAuth 2.1系を用いた認証が必要なサービスとも連携が可能である
これにより、ローカルのツールだけでなく、インターネット上の各種SaaS（クラウドサービス）をAIが直接操作できる
ドキュメントには「HTTP MCPサーバー」や「OAuth認証」への対応が明記されている
**ポイント**
ローカル環境に閉じない、広範なツール接続性。
安全な認証プロトコル（OAuth 2.1）のサポート。
モダンなクラウド開発環境との親和性が高い。

### 8. 煩雑な認証処理の代行：SaaS連携におけるHermesの役割
クラウドサービス（Inngest, Sentry, Atlassian, Figma, Stripe等）はログイン認証が必要になる
これらのサービスとの連携には、OAuth、キー、トークンリフレッシュなどの複雑な手続きが伴う
Hermesはこれらの面倒な認証周りの手続きを肩代わりする設計になっている
,
開発者が個別に認証ロジックを実装しなくても、Hermesを介してセキュアにサービスを利用できる
これにより、ローカルツールからクラウド上のSaaSまでを一貫してAIの管理下に置くことができる
**ポイント**
複雑なトークン管理やリフレッシュ処理をHermes側でハンドリング。
開発者は「どのツールを使うか」に集中できる。
Googleログイン等の一般的な認証基盤と同じ感覚でSaaSを統合。

### 9. 既存AIツール（Claude/Cursor/Codex）とHermesのポジショニング比較
既存のツールとHermesは、MCPの使い方の目的が異なる
Claude Desktop / Cursor
目的：個人作業やエディタの補助。
特徴：手元の作業をAIに少し手伝ってもらう、アシスタント的な位置付け。
Claude Code / Codex
目的：コードを書くエージェントとしての実務。
特徴：リポジトリ操作やCLI実行など、開発現場に特化した強力な1本軸。
Hermes
目的：エージェントOSとして「作業チーム」の基盤を作る。
特徴：ツールを使うだけでなく、複数AIが動き続ける土台（メッセージ、看板等）との統合。
比較表 | ツール名 | 主な用途 | MCPの役割 | | :--- | :--- | :--- | | Claude Desktop/Cursor | 個人アシスタント | 補助ツールの追加 | | Claude Code/Codex | 開発・コーディング | 開発環境の操作 | | Hermes | チーム運営・自動化基盤 | エージェントOSの構成要素 |

### 10. 「エージェントOS」構想：メッセージ・記憶・ワークフローの統合
HermesはMCPを、単なる追加機能ではなく「OS（基本ソフト）」の一部として扱おうとしている
ここでいうOSとは、以下の要素が統合された環境を指す
メッセージ（通信基盤）
スキル（MCPによるツール群）
ワークフロー（作業の流れ）
看板（運用の可視化）
単発の会話ではなく、エージェントが24時間動き続け、成果を出し続けるためのプラットフォームを目指している
,
接続の先にある「複数エージェントをどう機能させるか」という問いへの回答がHermesである
**ポイント**
「点」のツール接続を、「面」のシステム統合へ。
AIが自律的に動くためのリソース管理をOSレベルで実施。
通信と記憶が最初から組み込まれている。

### 11. 看板（Kanban）による人間とエージェントの協調作業
運用の核心は「看板」を用いてタスクを回すことにある
同じファイルを介して、人間が見るボードとエージェントが動くボードが同期される仕組み
人間はボードで状況を俯瞰し、AIは裏側でそのボードのタスクを消化していく
誰がどのタスクを持ち、どこで詰まっているかが全てボードに残るため、進捗管理が透明化される
MCPで得た「手足」を使い、看板という「指令塔」の指示に従って作業チームが動く世界観である
**ポイント**
タスク管理の標準手法（看板）をAI運用に持ち込む。
人間とAIの役割分担が視覚的に明確になる。
全ての作業履歴がボードに集約されるため、引き継ぎが容易。
