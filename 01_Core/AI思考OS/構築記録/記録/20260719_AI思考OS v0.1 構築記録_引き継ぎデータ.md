# AI思考OS v0.1 構築記録

作成日: 2026-07-19

---

# 概要

本資料は、AI思考OS v0.1 がどのような経緯で設計され、どのような議論や試行錯誤を経て現在の形に至ったかを記録するための文書である。

最終成果物だけを見ると設計意図が失われるため、

* なぜ作ったのか
* 何に悩んだのか
* 何を採用し何を捨てたのか
* 今後どこを見直す可能性があるのか

を残すことを目的とする。

---

# 背景

もともとの目的は、

「AIを便利なツールとして使う」

ことではなかった。

目的は、

* 穏やかに生きる
* 自己観察を深める
* AIと共に成長する
* 人生の意思決定を支援する
* 知識を資産化する

ことであり、

AIはそのためのパートナーである。

そのため、

単なるプロンプト集ではなく、

長期的に育つ仕組みが必要になった。

---

# 初期段階の問題

AIとの対話を続ける中で、

同じ問題が何度も発生した。

主な問題は以下。

## 理解不足のまま提案する

AIが十分理解していない状態で、

改善案
提案
設計案

を出し始める。

結果として、

ユーザーが説明し直す。

---

## わかったふり

AIが理解したように振る舞うが、

実際には理解できていない。

結果として、

会話の後半で前提が崩れる。

---

## ループ

同じ確認を繰り返す。

同じ説明を何度も行う。

過去の議論が蓄積されない。

---

## 車輪の再発明

既に決まった内容を忘れ、

再び議論が始まる。

結果として、

知識が資産化されない。

---

# 問題の本質分析

議論を重ねた結果、

問題は個別ではなく構造的であると判断した。

つまり、

AIが

* ユーザーを理解していない
* 判断原則を持っていない
* 記憶管理がない

ことが根本原因である。

---

# User Model 構想の誕生

当初は、

AIにユーザー理解をさせる方法として

「ユーザープロファイル」

のようなものを考えた。

しかし検討を進める中で、

単なるプロフィールでは不十分と判明した。

必要なのは、

ユーザー情報ではなく、

ユーザーの判断構造である。

そこで、

User Model

という考え方が生まれた。

---

# User Model 肥大化問題

最初の案では、

User Model に

* 自分史
* 強み弱み
* 価値観
* 人生戦略
* AI戦略
* 宇宙の法則

などを大量に入れようとしていた。

しかし途中で問題が発生した。

User Model が第二の人生戦略OSになり始めたのである。

---

# 重要な気付き

議論の中で、

以下の結論に到達した。

人生戦略OSとUser Modelは別物である。

人生戦略OSは詳細資料。

User Modelは圧縮版。

この役割分離が重要である。

---

# 人生戦略OSとの関係整理

最終的に、

人生戦略OSを唯一の一次情報源とすることになった。

User Modelは、

人生戦略OSを要約したもの。

つまり、

# Source of Truth

人生戦略OS

となった。

---

# Pure OS Townとの統合問題

並行して、

Pure OS Town構想も進行していた。

その結果、

以下の概念が並立する状態になった。

* Pure OS Town
* AI思考OS
* User Model
* Memory Policy
* Failure Library
* Decision Log
* KnowledgeOS

このままでは管理不能になる可能性があった。

---

# 構造監査の実施

そこで、

各概念の責任範囲を整理した。

最終的に、

Pure OS Town
↓
AI思考OS
↓
User Model
↓
Memory Policy
↓
Decision Log / Failure Library
↓
KnowledgeOS

という階層が採用された。

---

# User Model ベンチマーク調査

途中で、

「世の中の先進事例はどうしているのか」

を調査した。

結果として、

完全一致する事例は見つからなかった。

しかし、

以下の近い考え方が存在した。

* Anthropic Constitutional AI
* Agent Memory
* Personal AI
* AI Copilot
* AgentOS系構想

結論として、

User Modelは既存事例の組み合わせに近いが、

現在の形はかなり独自性が高いと判断した。

---

# Memory Policy の誕生

次に問題となったのが、

どこに記録を保存するかだった。

---

# Grok問題

Grokは、

ローカルPCのファイルを直接読めない。

また、

ファイルを保存しても

勝手には見に行かない。

さらに、

attachments と artifacts の違いを認識できないことがある。

そのため、

ナレッジが存在するのに

「ファイルがありません」

と言う問題が発生した。

---

# Single Source of Truth 議論

様々な案を検討した結果、

当面は

Grok外部記憶

をSSoTとすることになった。

理由は、

現在Grok中心運用だからである。

ただし将来的には、

KnowledgeOSへ移行予定。

---

# Tier構造採用

記憶管理のため、

Tier構造を採用。

## Tier1

常時必要な情報

* AI思考OS
* User Model
* Core Values

など

---

## Tier2

要約保存

* Decision Log
* Failure Library

など

---

## Tier3

長期保管

* 会話ログ
* 実験記録
* リサーチ

など

---

# Grok運用上の知見

構築過程で、

Grok特有の知見も得られた。

## MOCが必要

Grokは存在を忘れる。

そのため、

チャット開始時に

どこに何があるか

を教える必要がある。

---

## 添付ファイルは強い

attachmentsは比較的安定。

Grokは添付されたものを参照しやすい。

---

## artifactsは作業領域

生成物や更新ファイルは

artifacts側に保存される。

---

---

## User Model

---

## AI思考OS

---

# 現時点での最大の学び

最も重要だった学びは、

「仕組みを増やすことではなく、責任範囲を明確にすること」

だった。

問題の多くは、

機能不足ではなく、

概念の重複から発生していた。

そのため、

新しいルールを増やすより、

役割を明確にした方が効果が大きかった。

これがAI思考OS v0.1構築で得られた最大の知見である。
