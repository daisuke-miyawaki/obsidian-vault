# AI思考OS v0.1 構築記録

作成日: 2026-07-19

---

# 概要

本資料は、AI思考OS v0.1 がどのような経緯で設計され、どのような議論や試行錯誤を経て現在の形に至ったかを記録するための文書である。

最終成果物だけを見ると設計意図が失われるため、

* なぜ作ったのか
* 何に悩んだのか
* 何を採用し何を捨てたのか
* 今後どこを見直す可能性があるのか

を残すことを目的とする。

本資料は仕様書ではなく、構築の歴史と設計判断を残すための記録である。

---

# 背景

もともとの目的は、

「AIを便利なツールとして使う」

ことではなかった。

目的は、

* 穏やかに生きる
* 自己観察を深める
* AIと共に成長する
* 人生の意思決定を支援する
* 知識を資産化する

ことであり、

AIはそのためのパートナーである。

そのため、

単なるプロンプト集ではなく、

長期的に育つ仕組みが必要になった。

---

# 初期段階の問題

AIとの対話を続ける中で、

同じ問題が何度も発生した。

## 理解不足のまま提案する

AIが十分理解していない状態で、

* 改善案
* 提案
* 設計案

を出し始める。

結果として、

ユーザーが説明し直すことになる。

---

## わかったふり

AIが理解したように振る舞うが、

実際には理解できていない。

結果として、

会話の後半で前提が崩れる。

---

## ループ

同じ確認を繰り返す。

同じ説明を何度も行う。

過去の議論が蓄積されない。

---

## 車輪の再発明

既に決まった内容を忘れ、

再び議論が始まる。

結果として、

知識が資産化されない。

---

# 問題の本質分析

議論を重ねた結果、

問題は個別ではなく構造的であると判断した。

つまり、

AIが

* ユーザーを理解していない
* 判断原則を持っていない
* 記憶管理がない

ことが根本原因である。

---

# User Model 構想の誕生

当初は、

AIにユーザー理解をさせる方法として

「ユーザープロファイル」

のようなものを考えた。

しかし検討を進める中で、

単なるプロフィールでは不十分と判明した。

必要なのは、

ユーザー情報ではなく、

ユーザーの判断構造である。

そこで、

User Model

という考え方が生まれた。

---

## User Modelとは

User Modelは、

AIがユーザーを理解するための圧縮モデルである。

価値観、
判断傾向、
人生方針、
思考特性などを要約し、

AIが意思決定支援を行う際の参照情報として利用する。

人生戦略OSの要約版であり、

一次情報源ではない。

---

# User Model 肥大化問題

最初の案では、

User Model に

* 自分史
* 強み弱み
* 価値観
* 人生戦略
* AI戦略
* 宇宙の法則

などを大量に入れようとしていた。

しかし途中で問題が発生した。

User Model が第二の人生戦略OSになり始めたのである。

---

# 重要な気付き

議論の中で、

以下の結論に到達した。

人生戦略OSとUser Modelは別物である。

人生戦略OSは詳細資料。

User Modelは圧縮版。

この役割分離が重要である。

---

# 人生戦略OSとの関係整理

最終的に、

人生戦略OSを唯一の一次情報源とすることになった。

User Modelは、

人生戦略OSを要約したもの。

つまり、

## Source of Truth

人生戦略OS

となった。

---

## 人生戦略OSとは

人生戦略OSは、

ユーザーの人生に関する知識、
経験、
価値観、
原則、
戦略を蓄積する基盤である。

本プロジェクトにおける唯一の一次情報源であり、

他の仕組みは人生戦略OSを参照する。

---

# AI思考OS 構想

User Modelだけでは、

ユーザー理解はできても、

AIがどう判断するかは定義できなかった。

そこで必要になったのが、

AI思考OSである。

---

## AI思考OSとは

AI思考OSは、

AIが提案や分析を行う際の判断原則である。

何を優先し、

何を避け、

どのような順序で考えるかを定義する。

User Modelが

「誰を支援するか」

を表すのに対し、

AI思考OSは

「どのように考えるか」

を定義する。

---

# Pure OS Townとの統合問題

並行して、

Pure OS Town構想も進行していた。

その結果、

以下の概念が並立する状態になった。

* Pure OS Town
* AI思考OS
* User Model
* Memory Policy
* Failure Library
* Decision Log
* KnowledgeOS

このままでは管理不能になる可能性があった。

---

# 構造監査の実施

そこで、

各概念の責任範囲を整理した。

最終的に、

Pure OS Town
↓
AI思考OS
↓
User Model
↓
Memory Policy
↓
Decision Log / Failure Library
↓
KnowledgeOS

という階層が採用された。

---

## Pure OS Townとは

人生戦略OS、
AI思考OS、
KnowledgeOSなどを包含する最上位思想である。

全体の方向性とガバナンスを担う。

---

# User Model ベンチマーク調査

途中で、

「世の中の先進事例はどうしているのか」

を調査した。

結果として、

完全一致する事例は見つからなかった。

しかし、

以下の近い考え方が存在した。

* Anthropic Constitutional AI
* Agent Memory
* Personal AI
* AI Copilot
* AgentOS系構想

結論として、

User Modelは既存事例の組み合わせに近いが、

現在の形はかなり独自性が高いと判断した。

---

# Memory Policy の誕生

次に問題となったのが、

どこに記録を保存するかだった。

---

## Memory Policyとは

どの情報を、

どこに、

どの粒度で保存するかを定義するルールである。

AIの記憶管理を統一し、

重複保存や記憶喪失を防ぐ。

---

# Grok問題

Grokは、

ローカルPCのファイルを直接読めない。

また、

ファイルを保存しても

勝手には見に行かない。

さらに、

attachments と artifacts の違いを認識できないことがある。

そのため、

ナレッジが存在するのに

「ファイルがありません」

と言う問題が発生した。

---

# Single Source of Truth 議論

様々な案を検討した結果、

当面は

Grok外部記憶

を運用上の中心記憶とすることになった。

理由は、

現在Grok中心運用だからである。

ただし将来的には、

KnowledgeOSへ移行予定である。

---

# Tier構造採用

記憶管理のため、

Tier構造を採用した。

## Tier1

常時必要な情報

* AI思考OS
* User Model
* Core Values

など

---

## Tier2

要約保存

* Decision Log
* Failure Library

など

---

## Tier3

長期保管

* 会話ログ
* 実験記録
* リサーチ

など

---

# Failure Library 構想

AIとの運用の中で、

同じ失敗が繰り返される問題が発生した。

そこで、

失敗を知識として蓄積する仕組みが必要になった。

---

## Failure Libraryとは

AI運用上の失敗パターン集である。

* わかったふり
* 理解不足の提案
* ループ
* 前提崩壊

などを記録し、

再発防止に利用する。

---

# Decision Log 構想

車輪の再発明を防ぐため、

意思決定を記録する仕組みが必要になった。

---

## Decision Logとは

重要な判断の履歴である。

何を決めたかだけではなく、

なぜそう決めたかを残す。

同じ議論の再発生を防ぐことを目的とする。

---

# KnowledgeOS 構想

最終的な知識資産の保管先として、

KnowledgeOS構想が生まれた。

---

## KnowledgeOSとは

知識資産の保管・接続基盤である。

単なる保管庫ではなく、

知識同士をリンクし、

再利用可能な形で蓄積することを目的とする。

将来的にはObsidianとの統合も想定している。

---

# Grok運用上の知見

構築過程で、

Grok特有の知見も得られた。

## MOCが必要

Grokは存在を忘れる。

そのため、

チャット開始時に

どこに何があるか

を教える必要がある。

---

## 添付ファイルは強い

attachmentsは比較的安定。

Grokは添付されたものを参照しやすい。

---

## artifactsは作業領域

生成物や更新ファイルは

artifacts側に保存される。

---

# 保管場所方針（Storage Policy）

本プロジェクトでは、

概念の責任範囲だけではなく、

保管責任も明確化する。

将来的にHermes AgentやKnowledgeOSへ移行する際の基準とする。

| 概念              | 現在の保管先   | 将来の保管先       | 正本              |
| --------------- | -------- | ------------ | --------------- |
| 人生戦略OS          | 未整備      | KnowledgeOS  | 人生戦略OS          |
| User Model      | Grok外部記憶 | 人生戦略OS配下     | 人生戦略OS          |
| AI思考OS          | Grok外部記憶 | Governance領域 | AI思考OS          |
| Decision Log    | 未整備      | KnowledgeOS  | Decision Log    |
| Failure Library | 未整備      | KnowledgeOS  | Failure Library |
| Memory Policy   | Grok外部記憶 | Governance領域 | Memory Policy   |
| KnowledgeOS     | 構築予定     | KnowledgeOS  | KnowledgeOS     |

# 現時点での最大の学び

最も重要だった学びは、

「仕組みを増やすことではなく、責任範囲を明確にすること」

だった。

問題の多くは、

機能不足ではなく、

概念の重複から発生していた。

そのため、

新しいルールを増やすより、

役割を明確にした方が効果が大きかった。

これがAI思考OS v0.1構築で得られた最大の知見である。
