# エコシステム運用ルール v0.1

## 目的

ナレッジを**より楽に・より早く・省エネで集め、何年後も把握し続ける**ための具体ルールを定める。

上位方針：Pure OS Town 憲法第9条（エコシステム推進）および `wiki/Principles/EcosystemAdvancement.md`。  
本ファイルは**法律（具体）**。憲法の言い換えではなく、現場の手順を書く。

---

## 1. 役割分担

| 層 | 置くもの |
|----|----------|
| Town憲法 | 「常に進める」方針 |
| 本ルール（AI思考OS） | 何を・どこに・どう更新するか |
| `02_活動基盤/運用/テンプレート/` | YAML／MOCのひな形 |
| 各領域の `MOC_*.md` | 過去を含む棚卸し地図 |

---

## 2. MOC（必須）

1. 領域MOCを持つ：Core／素材庫／発信／Inbox／アイデア／その他  
2. お客は**一覧MOCを作らない**。お客フォルダ内の `MOC_お客さん.md` に過去ファイルを列挙する  
3. MOCはフォルダ名だけの地図で終わらせない。**中身の塊・主要ノートを載せる**  
4. 件数が多い棚（YouTube等）は、上位MOC＝チャンネル単位、詳細＝各 `_index.md`  
5. **新しい塊を足したら、該当MOCにその日のうちに1行追加する**

---

## 3. YAML（必須の向き）

1. 種類別テンプレに従う（`運用/テンプレート/00_目次.md`）  
2. **新規ノート**および**今日触ったノート**にはYAMLを付ける  
3. 過去の一括埋め直しは必須ではないが、触ったものはそのとき直す  
4. 人生戦略OSの番号ファイルはYAML必須にしない（番号体系で足りる）

---

## 4. 置き場

| 種類 | 置き場 |
|------|--------|
| MTG・録音・会話 | お客フォルダの進行中／過去案件（独自の大棚を作らない）→ お客MOCへリンク |
| 素材 | `03_素材庫`（宇宙の法則／心理学・脳科学・潜在意識／マーケティング／AI・ツール／講座／Inbox） |
| 発信 | `02_活動基盤/発信` |
| 仮置き（Vault全体） | `04_Inbox`（**§4.0**：分類できないものだけ） |
| 素材のおまかせ分別 | `03_素材庫/Inbox/おまかせ/`（下記§4.1） |

### 4.0 Inboxの原則（最重要）

**Inboxは「置き場がまだ決められないもの」専用である。何でもかんでも入れない。**

| 判断 | すること |
|------|----------|
| **行き先がわかる** | Inboxに入れない。最初から正しい場所へ置く |
| **分類できない／迷う** | そのときだけ `04_Inbox`（または素材の `おまかせ/`）へ入れる |
| **あとで振り分ける前提で一旦全部Inbox** | **禁止** |

**行き先がわかる例（Inbox禁止）**

- AI思考OSのルール正本 → `01_Core/AI思考OS/` 直下  
- 構築の①経緯／②仕組み → `構築記録/ルール作り_経緯/` または `ルール作り_仕組み/`（`構築記録の置き方 v0.1`）  
- VPS作業の経緯 → `02_活動基盤/運用/作業ログ_マルチエージェントVPS.md` など既存作業ログ  
- 運用の繰り返し手順 → `02_活動基盤/運用/プレイブック_*.md`  
- 顧客案件とわかるもの → 該当お客フォルダ（AIは独断で移さない。人間が行き先を決める）

**AIへの拘束**

1. 新規保存・移動の提案をするとき、まず「行き先は分かるか？」を自分で答える  
2. 分かるなら Inbox を提案しない。正しい場所を提案する  
3. 分からないときだけ Inbox／おまかせを提案し、**何が不明か**を短く書く  
4. 「とりあえずInbox」は失敗パターンとして扱わない（やってはいけない）

### 4.1 おまかせ分別（AIがやってよいこと）

場所：`03_素材庫/Inbox/おまかせ/`

**人間がやること**  
中にファイルを入れる（または「おまかせを分別して」と指示する）。  
※ 素材テーマがすでに分かるファイルは、おまかせを経由せず該当テーマへ直接置いてよい。

**AIがやってよいこと**  
1. `おまかせ/` だけを対象にする  
2. 既存の素材テーマ（宇宙の法則／心理学・脳科学・潜在意識／マーケティング／AI・ツール／講座）のどれかに移す  
3. 迷ったら移さず残すか、報告で聞く  
4. 必要ならYAML付与・該当MOCへの1行追加案まで行う  
5. 作業後、短い報告を出す（何をどこへ／残したもの／迷った理由）

**AIがしないこと（独断禁止）**  
1. アーカイブ／削除（資産にならない判断は人間）  
2. **お客さんフォルダへの投入** … `02_活動基盤/実務/お客さん情報/{名前}/` へ勝手に移さない。お客案件っぽいものは報告し、人間が「このお客へ」と決めてから移す  
3. 新しい大テーマ（素材庫の第1階層）の新設  

`おまかせ/` 以外の Inbox 直下ファイルは、人間が先に見る／保留用。AIは指示があるまで勝手に全部動かさない。  
ただし **新規に「分かるファイル」を Inbox 直下へ足す提案はしない**（§4.0）。

---

## 5. 資産と非資産

1. AIはナレッジ化（整える・要約・置き場案）を助ける  
2. **資産にならない**ものの最終判断は人間。`06_アーカイブ` へ移す  
3. お客の過去案件は `06` に流して忘れない。お客フォルダ内で資産化する  
4. **構築記録は資産**（仕組みを作った経緯・仕様・引き継ぎ）。古い／作業メモだからといって `06_アーカイブ` へ流さない。置き場は `01_Core/AI思考OS/構築記録/`  
   - **①経緯**と**②仕組み**は分けて保存する。正本ルール：`構築記録の置き方 v0.1.md`  
   - 地図：`構築記録/00_入口_構築記録.md`  
   - 新規のルール作り記録を `記録/` 直下やInboxへ適当に増やさない

---

## 6. 読み込みとの関係

チャット開始時の「何を読むか」は `プレイブック_ナレッジ読み込みパターン.md` に従う。  
エコシステムは「集め・把握する側」。読み込みは「今日使う側」。両方必要。

---

## 7. Obsidian

将来のObsidian利用を前提に、YAML先頭＋`[[wikilink]]`＋MOCを標準とする。  
特定プラグイン必須にはしない。

---

## 8. やらないこと

- 「検索できるからMOC不要」と言う  
- エコシステム完成を待って収集を止める  
- Town憲法にYAMLの細部を書き込む  
- 構築記録の奥に正本を隠す  
- **行き先がわかるファイルを Inbox に入れる**（§4.0）  
- 「とりあえずInbox」で保存する
